**병행 예측 검증의 범위와 해석**

실행 파일: `../validate_prediction.py`. 입력·모델·소스 SHA는 protocol.json에 고정했다. 상태는 status.json, 진행 로그는 stdout.log, 진단은 stderr.log, 최종 보고서는 report.md와 results.json에 저장한다.

기존 CUDA PPO 프로세스는 재시작하거나 수정하지 않는다. 검증은 GPU를 숨긴 별도 프로세스(CUDA_VISIBLE_DEVICES=-1), CPU 계산 스레드 1개, Windows BelowNormal 우선순위로 실행한다. 운영체제 자원을 일부 공유하므로 학습 시간에 영향이 전혀 없다고 보장하는 방식은 아니며, 부하를 제한하는 방식이다.

기존 검증 관측 8회를 재생하여 다음을 비교한다.

- 제공 1,200 step Transformer: 기존 비교 수치의 재현 확인용.
- 2,800 step 사전학습 best Transformer.
- PPO 176 update Transformer.
- 시작 시점에 고정한 PPO 190 update Transformer. 작업이 진행되어도 이 비교 대상은 바꾸지 않는다.
- 기존 LightGBM 및 176 Transformer와의 확률 혼합.

첫 실행은 GPU 접근 차단 확인 단계에서 중단됐고, 실제 검증용 추론에 들어가기 전에 로그가 보존됐다. Windows에서 빈 CUDA 환경값 대신 -1을 쓰는 새 실행(v2)으로 변경했다. 원본 학습 코드·체크포인트·해시를 고친 복구가 아니다.

**읽을 때 구분할 사항**

1. AP·확률 보정·분류 성능은 동일 링크/시점/정답 표본으로 비교한다. Transformer의 원래 지원 범위와 LightGBM과의 공통 범위도 별도 기록한다.
2. LightGBM은 과거 512,000개 feature window로 학습된 체크포인트이고, Transformer는 다른 학습 이력을 가진다. 실제 후보 예측기의 성능 비교이며, 동일 데이터·예산으로 학습한 모델 구조의 우열을 증명하는 실험은 아니다.
3. LightGBM의 원래 확률 보정은 과거 자료에서 학습됐다. 첫 검증에서는 새 보정기를 학습하지 않고 기존 확률을 평가한다. 필요시 독립 공간 그룹에서 보정을 추가 비교한다.
4. 네 공간 fold에서 혼합 비율과 경보 문턱을 나머지 6개 맵으로 조정하고 남은 2개 맵에 적용한다. 같은 8개 맵이 이전 checkpoint 선택에 사용된 이력까지 제거하는 것은 아니다.
5. 기존 임계값 조건과 더 엄격한 개발 목표를 각각 진단한다. 실제 운영 경보를 활성화하거나 현재 PPO 입력에 혼합을 넣지 않는다.
6. 1~6 방향성 중 현재 실행하는 것은 데이터·평가 계약 확인, 동일 관측 예측 비교, 혼합 후보 예비 검증, 경보/확률 보정 진단이다. 손실·모델 크기·PPO 결합 방식의 재학습은 아직 실행하지 않는다. 첫 검증 결과로 무엇을 바꿀지 정한다.
7. 최종 holdout 자료는 읽지 않는다. 전체 96조건 검증과 최종 테스트를 완료한 결과로 해석하지 않는다.

report.md가 없는 동안은 검증이 끝나지 않은 상태다. 실패 시 status.json과 stderr.log에 이유를 남기며, 해시나 오류를 무시하고 결과를 계속 만들지 않는다.
